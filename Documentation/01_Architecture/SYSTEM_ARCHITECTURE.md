# Системная архитектура MIR Preventive

## 1. Архитектурная модель

Платформа строится как набор независимых доменных подсистем с явными контрактами данных и событий.

```text
┌───────────────────────────────────────────┐
│                    UI                     │
└─────────────────────┬─────────────────────┘
                      │
┌─────────────────────▼─────────────────────┐
│             Preventive Orchestrator       │
└───────┬───────────┬───────────┬───────────┘
        │           │           │
   Diagnostics   BioModel   RiskEngine
        │           │           │
        └──────┬────┴──────┬────┘
               │           │
        PreventiveEngine   AI Supervisor
               │           │
               └─────┬─────┘
                     │
              Medical Routing
                     │
                  User/Clinician

Cross-cutting: Security · Consent · Audit · Data Provenance · Event Bus
```

## 2. Core domain objects

Минимальное ядро должно включать:

- `Person` — субъект наблюдения;
- `Observation` — первичное наблюдение;
- `Measurement` — измерение с единицей и методом;
- `QualityReport` — оценка качества;
- `DerivedMetric` — вычисленный показатель;
- `Trend` — временная динамика;
- `RiskSignal` — риск-сигнал;
- `Recommendation` — рекомендация;
- `Referral` — маршрутизация;
- `ModelVersion` — версия модели;
- `Consent` — согласие;
- `AuditEvent` — событие аудита.

## 3. Поток данных

Данные движутся только через типизированные контракты. Нельзя передавать между подсистемами неструктурированный текст как единственный источник медицински значимой информации.

Каждый объект должен иметь идентификатор, timestamp, provenance и версию схемы.

## 4. Event Bus

Событийная модель позволяет разнести получение измерений, моделирование, анализ и UI.

Примеры событий:

- `SessionStarted`
- `MeasurementCaptured`
- `MeasurementQualityEvaluated`
- `ObservationAccepted`
- `ModelUpdated`
- `TrendDetected`
- `RiskSignalCreated`
- `RecommendationGenerated`
- `MedicalReviewRequested`
- `SessionCompleted`

## 5. AI Supervisor

AI Supervisor находится над специализированными алгоритмами, но не подменяет их.

Его задачи:

- проверка полноты контекста;
- поиск противоречий;
- объяснение результатов;
- выбор следующего программного шага;
- контроль соблюдения safety-контрактов;
- формирование понятного пользовательского представления.

AI не может изменять исходные измерения и не может создавать отсутствующие данные.

## 6. Deterministic Core

Критически важные преобразования должны иметь детерминированные компоненты, пригодные для unit/property/reproducibility testing. AI допускается там, где он действительно добавляет ценность и где его неопределённость может быть явно представлена.

## 7. Data Provenance

Для каждого производного результата хранится цепочка происхождения:

`result → algorithm/model version → input observations → sensor/source → timestamp`

Это позволяет повторно вычислить результат и провести аудит.

## 8. Security Boundary

Безопасность является отдельным архитектурным слоем. Доступ к данным должен предоставляться по принципу минимально необходимых полномочий.

## 9. Offline-first возможность

Архитектура должна допускать локальную обработку чувствительных данных с последующей передачей только разрешённого пользователем набора данных. Потеря соединения не должна разрушать целостность локальной диагностической сессии.

## 10. Масштабирование

Новые сенсоры, модели и алгоритмы подключаются через интерфейсы, а не через изменение всего приложения. Это позволяет строить разные конфигурации станции для разных задач без переписывания ядра.
